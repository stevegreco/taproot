# Divider run: process notes

Running log while building Divider spec-first (PR #241). Likes (+), dislikes (-), spec issues (S), observations (o). Divider is the smallest component so far, which makes it a good test of how much ceremony the process costs for something trivial.

## Orientation
- (+) Same as the other runs: AGENTS.md plus the three skills was enough to start without asking anything.
- (o) This run was told not to touch the package root index, so the other three new components don't conflict. That turned out to touch more than "the barrel" (see Cross-cutting).

## Phase 1: spec
- (+) `spec search separator` and `spec search "horizontal rule"` found nothing before the draft and Divider right after, using only the draft's tags. Tags are doing real work for search.
- (S) compose-or-propose doesn't clearly decide Divider, the same way it didn't decide Card. Step 3 ("product layout styled with semantic tokens") literally covers drawing a line. I justified it on the accessibility decision (separator role and orientation) and forced colors, but the guideline's "propose" list has no bucket for "trivial visually, but has a semantic role every hand-drawn copy gets wrong". Third run to hit this; the guideline needs a line for presentational components.
- (S) Anatomy roles again: a line is not an `indicator` (it shows no state), a `container`, a `label` or a `description`. I used `indicator`. Spinner and Card hit the same closed list. A `graphic` or `decoration` role would cover Divider, Spinner's arc and Card's media.
- (S) The draft is supposed to leave out parameters, but whether vertical exists is part of what Divider *is* (it changes the description and the do list). Same gap Accordion hit. I wrote it into the description prose.
- (-) Prose `instead` has a hidden grammar: it renders as "Use <text> instead.", so it must be a lowercase noun phrase ("space from the layout", "a heading for each section"). Card's notes flagged this too. One line in the skill would fix it.
- (o) Two of the four avoid entries point at "not a component" answers (layout spacing, list borders). For a layout primitive, most of the boundary is "use layout", not "use another component". The format handles that fine as prose.

## Phase 2: implementation
- (+) The decide-what-it-ships checklist closed in one pass with `covers:`. For a trivial component, seven of ten items are "not applicable", and `covers: [disabled, selected, loading, invalid]` on one entry kept that short. Good design.
- (-) But it still costs ten rationale entries for a line. A shorthand like `not-applicable: [disabled, selected, loading, invalid, reduced-motion, right-to-left, icon-only]` with one shared reason would cut the noise for presentational components.
- (+) The scaffold was correct this time: camelCase issue doesn't apply (one-word parameter), the enum host-check row was right, and the tests file had one failing test per MUST rule.
- (-) The scaffold put the host-checks row at the top of the table, and the index entries at the end of index.js and index.d.ts. All four parallel components get the same insertion points, which is exactly where conflicts came from last time. I moved the row next to its alphabetical neighbour by hand. The scaffold should insert alphabetically.
- (S) `exposedNodes()` returns only role and name, so the one thing that distinguishes a vertical divider for assistive tech (orientation) couldn't be tested through it. I added an opt-in `exposedNodes({ properties: true })` (default shape unchanged, because ~20 existing assertions compare exact `{ role, name }` objects). Accordion asked for this too. The docs-site copy of the helper (`apps/documentation/examples/accessibility.js`) is a hand-mirrored duplicate and didn't get the option, so the Verify steps can't check orientation.
- (S) Token map has no property for "the line's color". I used `border` + `border-width`, which is what the CSS does, but a reader of the spec can't tell the border *is* the component. Same gap Accordion hit with its chevron.
- (S) Geometry is the whole contract for a divider (full width, full row height, one border width thick, no margin), and the format says geometry is "not a token property, state it as a rule". That worked: `spans-container` became a testable MUST rule. Good outcome, but nothing hints at it in the skill until you read the gotchas.
- (S) **Found a real token bug through `--resolve` plus a screenshot, not through any check:** dark `border.subtle` is 1.06:1 on `background.surface`, so a divider inside a Card is invisible in dark mode. Filed #245 and recorded it under `known-issues`, which was the right tool and rendered nicely in `spec get`. But nothing in the process computes contrast between the tokens a component puts next to each other. `spec tokens --resolve` already has both values; a contrast column against the surface the part sits on would have caught it immediately.
- (-) `validate` still doesn't check token references (Card, Accordion and the report all flagged this). Divider only uses two, so it didn't bite, but `--resolve` is still the only check.
- (-) Environment, same as every run: Playwright wants chromium build 1234, the cloud image has 1194, and turbo's strict env mode drops `PLAYWRIGHT_BROWSERS_PATH`. This time even symlinking the folder failed, because the headless shell binary was renamed between builds (`headless_shell` became `chrome-headless-shell`, in a renamed folder). I had to rebuild the folder layout by hand. A `passThroughEnv` entry and a pinned Playwright version that matches the image would save every agent run ten minutes.
- (-) "Check the Accessibility panel in both themes" still assumes a human. I scripted axe over the built Storybook again (5 stories x 2 themes, no violations). Third run that wrote this script; it should be `pnpm storybook:a11y`.

## Phase 3: docs
- (+) The docs scaffold plus `-t "the divider example"` loop is still fast and clear.
- (-) "Break each step once" is mostly theatre when done by editing the expected value: of course a step fails if you expect 999. The meaningful break is mutating the component (drop `align-self: stretch` and watch the vertical step fail), which needs a rebuild per break. The skill could say which kind it means.
- (-) The scaffold's hint "check whether custom-elements.d.ts needs an entry" is still misleading (Card flagged it). JSX types come from `ElementAttributes` in `index.d.ts`, which is the barrel, which this run wasn't allowed to touch.

## Cross-cutting
- (S) **"Don't touch the barrel" is not cleanly possible today.** Leaving `index.js`/`index.d.ts` out breaks three things, not one: `package-root.test.js` (registration), `example-types.test.ts` (JSX types come from `ElementAttributes` in `index.d.ts`), and Storybook and the docs example, which only import the package root and so would render nothing. I added a stopgap `defineDivider()` in the story and the example so they work, and listed the exact index entries in the PR. The PR carries two expected red tests until the final barrel PR. Options for the system: generate the index from `src/*.js` at build time (then there is no barrel to conflict on), or let the scaffold insert alphabetically so parallel PRs touch different lines.
- (o) The final barrel PR has an ordering problem: it can't land before the component PRs (the files don't exist on main), and the component PRs are red until it lands. Either merge the component PRs red and then the barrel PR, or stack the barrel PR on top of all four branches.
- (S) Known issues worked well: the format had exactly the right place for a problem found mid-build that isn't this component's to fix, and `spec get` shows it under the summary. Nice.
- (o) For a component this small, the spec (145 lines of YAML) is longer than the runtime and CSS together (~100 lines). Most of it is rationale for things that don't apply. That's the clearest signal so far that the format's cost is fixed per component, not proportional to complexity.
