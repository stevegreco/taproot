title: Semantic Tokens
description: Choose intent-based color, typography, elevation, and shape roles for product interfaces.
---

Semantic tokens describe what a visual decision is **for**. They are the normal styling API for
components and product interfaces because their intent remains stable when themes or primitive
values change.

:::note
Choose a token because its name matches the role, not because its current value looks right.
:::

## Choose a semantic token

1. Identify the CSS property you need to style.
2. Name the role that property serves in the interface.
3. Choose from the matching semantic group.
4. Use a primitive only when no semantic contract expresses that role.

Keep application groups separate: backgrounds style fills, foregrounds style visible content, and
borders style boundaries.

```css
.card {
  background: var(--semantic-color-background-surface);
  border: 1px solid var(--semantic-color-border-subtle);
  color: var(--semantic-color-foreground-default);
  border-radius: var(--semantic-radius-surface);
  box-shadow: var(--semantic-elevation-sm);
}
```

## Color

Semantic colors are organized by the property they style and the intent they communicate.

| Group      | Use for                                           | Example                               |
| ---------- | ------------------------------------------------- | ------------------------------------- |
| Background | Fills behind content                              | `--semantic-color-background-surface` |
| Foreground | Text, icons, and SVG content                      | `--semantic-color-foreground-muted`   |
| Border     | Borders, dividers, outlines, and focus indicators | `--semantic-color-border-focus`       |

### Background

Background roles describe the purpose of a fill. Foundation roles establish page structure; brand,
action, and status roles communicate more specific intent.

| Family             | Roles                                               | Use for                                                                |
| ------------------ | --------------------------------------------------- | ---------------------------------------------------------------------- |
| Foundation         | `default`, `surface`, `sunken`, `muted`, `disabled` | Page hierarchy, containers, recessed regions, and unavailable controls |
| Brand              | `default`, `muted`                                  | Prominent and quiet branded surfaces                                   |
| Primary action     | `default`, `hover`, `pressed`                       | The strongest action in a context                                      |
| Secondary action   | `default`, `hover`, `pressed`                       | Opaque supporting actions                                              |
| Tertiary action    | `hover`, `pressed`                                  | Low-emphasis actions that are transparent at rest                      |
| Destructive action | `default`, `hover`, `pressed`                       | Actions that delete or cause irreversible change                       |
| Status             | `success`, `warning`, `info`, `danger`              | Quiet feedback and messaging surfaces                                  |

Every interactive state has one semantic token. Secondary actions publish opaque default, hover,
and pressed fills. Tertiary actions remain transparent at rest and publish direct hover and pressed
fills. Destructive action fills and danger-status fills are separate contracts: one signals an
action, while the other communicates a condition.

<SemanticTokenReference kind="background" />

```css
.primary-action {
  background: var(--semantic-color-background-action-primary-default);
}

.primary-action:hover {
  background: var(--semantic-color-background-action-primary-hover);
}
```

### Foreground

Foreground roles style visible content. Use an explicit `on` token when content sits on a strong
brand or action fill.

| Family     | Roles                                  | Use for                                              |
| ---------- | -------------------------------------- | ---------------------------------------------------- |
| Foundation | `default`, `muted`, `disabled`         | Primary, supporting, and unavailable content         |
| Brand      | `default`                              | Branded text or icons on compatible neutral surfaces |
| On brand   | `default`                              | Content placed on the default brand background       |
| On action  | `primary`, `destructive`               | Content placed on strong action fills                |
| Status     | `success`, `warning`, `info`, `danger` | Status-colored text and icons                        |

Do not choose a foreground by contrast alone. Its name must identify the background family it
supports.

<SemanticTokenReference kind="foreground" />

```css
.primary-action {
  color: var(--semantic-color-foreground-on-action-primary);
}
```

[Review supported foreground pairings in the lab](/labs/foreground).

### Border

Border roles style visible boundaries. Functional boundaries must remain distinguishable from
their supported surfaces; decorative boundaries must not be the only visual cue.

| Family             | Roles                                              | Use for                                                                  |
| ------------------ | -------------------------------------------------- | ------------------------------------------------------------------------ |
| Foundation         | `default`, `strong`, `subtle`, `disabled`, `focus` | Controls, emphasis, decoration, unavailable states, and focus indication |
| Primary action     | `default`, `hover`, `pressed`                      | Primary action boundaries                                                |
| Destructive action | `default`, `hover`, `pressed`                      | Destructive action boundaries                                            |
| Brand              | `muted`                                            | Decorative brand boundaries                                              |
| Status             | `success`, `warning`, `info`, `danger`             | Feedback and messaging boundaries                                        |

### Supported status pairings

status family when composing feedback surfaces; the shared intent communicates the pairing rather

## Typography

Typography tokens are complete recipes. Each recipe publishes `font-family`, `font-size`,
`font-weight`, `line-height`, and `letter-spacing` leaves beneath the same semantic path.

| Recipe  | Variants                    | Use for                                 |
| ------- | --------------------------- | --------------------------------------- |
| Heading | `large`, `default`, `small` | Page and section hierarchy              |
| Body    | `default`, `small`          | Reading and supporting copy             |
| Label   | `default`, `small`          | Controls, metadata, and compact UI text |
| Eyebrow | —                           | Short overlines and category labels     |
| Code    | `default`, `small`          | Code and machine-readable values        |

Apply all five leaves when adopting a recipe. Swap the whole recipe when the text role changes.

<SemanticTokenReference kind="typography" />

```css
.card-title {
  font-family: var(--semantic-typography-heading-sm-font-family);
  font-size: var(--semantic-typography-heading-sm-font-size);
  font-weight: var(--semantic-typography-heading-sm-font-weight);
  line-height: var(--semantic-typography-heading-sm-line-height);
  letter-spacing: var(--semantic-typography-heading-sm-letter-spacing);
}
```

## Theming

Semantic color and elevation tokens resolve to the active theme. Consumers keep the same token
names when switching between light and dark.

```html
<html data-theme="dark"></html>
```

```js
document.documentElement.setAttribute("data-theme", "dark"); // Dark theme
document.documentElement.setAttribute("data-theme", "light"); // Light theme
document.documentElement.removeAttribute("data-theme"); // Follow the system setting
```

Typography and shape mappings are theme-independent. For an intentionally always-dark region,
define local aliases with known contrast relationships instead of relying on the global theme
switch.
